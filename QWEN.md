# QWEN.md — контекст для работы над Ouroboros

> Это инструкционный контекст для агентов и людей, работающих над репозиторием
> Ouroboros. **Перед любыми правками обязательно прочитайте `CONTRIBUTING.md`**
> (см. ниже «Обязательное чтение перед правками»).

## Обзор проекта

**Ouroboros** — открытый универсальный AI-агент общего назначения, который
обладает саморедактируемой реализацией: неизменная личность, долговременная
память и история сохраняются между задачами и перезапусками. Он работает над
внешними проектами, координирует живой «рой» специализированных субагентов и
может переписывать собственную реализацию (код, архитектуру, промпты, инструменты
и зависимости).

Ключевые характеристики (детали — в документации проекта):

- Самоизменяющаяся «поверхность»: код, промпты, инструменты, зависимости;
  рефлексия может менять и самопонимание агента.
- Автономная эволюция: кампании эволюции превращают улучшения в рецензируемые
  изменения, остающиеся в git-истории.
- Непрерывность между перезапусками: личность, память, диалоги, знания,
  рефлексии и история версий — одна непрерывная биография.
- Фоновая «сознательность» между запросами: рефлексия, инициатива и подготовка.
- Работа над внешними проектами: отдельный git-worktree может принять полный
  цикл задачи, пока сам Ouroboros сохраняет собственный репозиторий и границы
  управления.
- Работа через десктопный клиент или headless CLI.

Запускается как нативное десктопное приложение или headless CLI. Рантайм хранит
репозиторий, память и интерфейс на машине пользователя; инференс модели идёт либо
через настраиваемые удалённые API, либо через локальную GGUF-модель.

Ouroboros использует **Claudexor** как локальный слой исполнения для делегированного
кодинга и хостинговой рецензии: Ouroboros владеет задачей, памятью, рецензией и
финальной интеграцией, а Claudexor запускает подключённый хостинговый coding-harness
и возвращает долгосрочные свидетельства исполнения.

## Технологии и версии

- **Язык:** Python ≥ 3.10.
- **Резолвер зависимостей:** `uv`, версия жёстко закреплена (`[tool.uv] required-version = "==0.12.1"`).
- **Веб/сервер:** Starlette + uvicorn (саморедактируемая точка входа `server.py`).
- **Десктоп:** pywebview (`launcher.py` — неизменяемый десктопный лаунчер).
- **CLI:** `ouroboros.cli:main`.
- **Тесты:** pytest (+ pytest-xdist, pytest-timeout), маркеры по «полосам».
- **Линт:** ruff.
- Текущая версия в файле `VERSION`: `6.114.0`.

## Структура репозитория

```text
ouroboros/          # базовый пакет (ядро): config, cli, server_*, review_*, skill_*,
                    #   subagent_*, workspace_*, gateway, tool_policy и т.д.
ouroboros/contracts/    # типизированные контракты (импульс: входящий Интерфейс)
ouroboros/gateway/      # входящий фасад HTTP/WebSocket для браузера и CLI:
                        #   contracts.py (типы), router.py (сборка роутов),
                        #   ws.py (WebSocket-трансляция)
ouroboros/gateways/     # тонкие исходящие адаптеры к внешним рантаймам
ouroboros/marketplace/  # интеграция с marketplace / OuroborosHub
ouroboros/tools/        # LLM-инструменты (тонкие функции `verb_noun`)
supervisor/         # супервизор runtime-процессов
web/                # фронтенд (HTML/JS/CSS, статика, katex, vendors)
tests/              # тесты (pytest)
scripts/            # вспомогательные скрипты (build_*, validate_scope_receipt,
                    #   run_external_review.py и др.)
devtools/benchmarks/   # адаптеры и методология бенчмарков
packaging/          # systemd-юнит и материалы упаковки
.github/workflows/  # CI: ci.yml, claudexor-platform-gate.yml и др.
```

Точки входа по `pyproject.toml`:
- `ouroboros = "ouroboros.cli:main"` — CLI/gateway.
- `ouroboros-web = "server:main"` — веб-сервер Web UI.

Данные рантайма по умолчанию: `~/Ouroboros/data`; сервер слушает
`127.0.0.1:8765` (порт задаётся переменными `OUROBOROS_SERVER_HOST` /
`OUROBOROS_SERVER_PORT`).

## Обязательное чтение перед правками

По `README` и `CONTRIBUTING.md` любой агент/человек, меняющий Ouroboros, обязан
прочитать перед редактированием:

- `CONTRIBUTING.md` — полный workflow pull-request (ветвление, верификация,
  отдельная рецензия, свидетельства).
- `docs/CHECKLISTS.md` — **полностью**; это единственный источник истины чек-листа
  рецензии (рецензент судит изменение именно по нему).
- `BIBLE.md` — конституционные принципы и приоритеты дизайна.
- `docs/ARCHITECTURE.md` — структура, потоки данных, обоснование неочевидных решений.
- `docs/DEVELOPMENT.md` — инженерные, тестовые и ревью-конвенции.
- `docs/DESIGN.md` — визуальная и интерактивная семантика.

Для четырёх последних: сначала карта по заголовкам, затем полное чтение каждого
раздела, релевантного конкретному изменению.

> Рекомендуемая первая инструкция код-агенту: «Прочитай CONTRIBUTING.md и
> docs/CHECKLISTS.md полностью. Составь карту BIBLE.md, docs/ARCHITECTURE.md,
> docs/DEVELOPMENT.md и docs/DESIGN.md по заголовкам и прочитай каждый раздел,
> релевантный запрошенному изменению, полностью. Следуй текущей архитектуре и
> держи изменение сфокусированным.»

## Подготовка окружения и запуск (from source)

Требования: Python ≥ 3.10, uv 0.12.1 (закреплённый резолвер этого checkout),
Git, по желанию `gh`.

```bash
# установка закреплённого резолвера uv
curl -LsSf https://astral.sh/uv/0.12.1/install.sh | sh

# клонирование и синхронизация (браузерные экстры + dev-группа)
git clone https://github.com/razzant/ouroboros.git
cd ouroboros
uv sync --locked --extra browser --group dev
source .venv/bin/activate

# запуск сервера (Web UI на http://127.0.0.1:8765)
ouroboros server
```

Headless CLI (gateway подключается к локальному рантайму; `--start` поднимает его):

```bash
ouroboros status
ouroboros run --start "2+2?"
ouroboros tasks list
ouroboros logs tail progress --task-id <task_id>
```

## Сборка и тестирование (Makefile)

```bash
make test      # быстрые smoke-тесты: uv run --locked python -m pytest tests/ -q --tb=short
make test-v    # то же, verbose
make lint      # детерминированный F-гейт (NameError-class): ruff check . --select F
make health    # код-хелс-чек (collect_sections / compute_complexity_metrics)
make clean     # очистка __pycache__ / .pytest_cache
```

### Тестовые маркеры (pytest)

Локальный запуск по умолчанию (`addopts` в `pyproject.toml`) исключает «дорогие»
маркеры. Соответствие полос CI:

- `integration` — реальные провайдерские ключи API; включается явно через
  `pytest -m integration`.
- `browser` — реальный Playwright Chromium.
- `ui_browser` / `ui_browser_docker` — реальный Web UI в host/direct или Docker.
- `serial` — реальный subprocess / реальный порт / мутация глобального состояния
  модуля; выполняется в serial-проходе, исключён из `-n auto` параллельного
  прохода (тот же two-pass split реализован и в hermetic-гейте
  `ouroboros/preflight_runner.py`). Тест, лишь «медленный», нужно ускорять/делить,
  а не переносить в unbounded serial-проход.
- `skill_smoke` — реальная установка официальных навыков OuroborosHub + ревью-smoke.
- `size_ratchet` — проверки размера репозитория; блокирующая полоса только в CI
  официального репозитория, локально те же проверки выводятся как предупреждения.
- `portable_detail` — детальные проверки portable/build-артефактов.

## Конвенции разработки (кратко, «источник истины» — docs/DEVELOPMENT.md)

- Идентификаторы кода, комментарии, docstrings и сообщения коммитов — **английские**.
  Пользовательские строки UI (web) — тоже английские.
  (Это конвенция *кода*; правила работы агента, включая QWEN.md, — на русском.)
- PEP 8: модули/переменные — `snake_case`, классы — `PascalCase`,
  константы — `UPPER_SNAKE_CASE`.
- LLM-инструменты — тонкие функции `{verb}_{noun}`, которые валидируют публичный
  вход, вызывают владеющего подсистему и форматируют результат. Без универсальных
  слоёв `{Domain}Service` / `{Platform}Gateway` / классов без жизненного цикла.
- Контракты — это типизированные фигуры (shapes), а не сервис-объекты. Менеджер
  оправдан, когда владеет жизненным циклом или изменяемым состоянием.
- Направление зависимостей: UI/CLI → входящий gateway → доменный владелец;
  политика runtime → маленький host-owned контракт → исходящий адаптер.
  Решения, специфичные для провайдера/транспорта, не должны просачиваться в
  базовую политику.
- Не чинить семантический сбой выбора инструмента добавлением ещё одной фразы в
  `prompts/SYSTEM.md` — добавлять типизированную affordance в нужной точке.
  Восстановимые сбои инструментов — свидетельство для следующего хода LLM, а не
  триггер host-authored recovery-воркфлоу.
- Не понижать качество модели, effort рассуждений и объём вывода для сознательности,
  ревью или самоэволюции как случайную оптимизацию задержки/цены.
- Принцип «общности и эмерджентности» (P13): стремиться решать класс проблемы,
  а не единственный случай; не плодить спекулятивные фреймворки.

## Workflow коммита и PR (сжато; полный текст — CONTRIBUTING.md)

1. **Прочитать** перечисленные выше документы до правок.
2. Одно связное изменение на PR; описание: проблема/возможность, что изменилось и
   почему соответствует архитектуре, что вне области видимости, риски (совместимость,
   миграция, безопасность, операции), точная верификация и её результат.
3. Ветка от нижнего регистра `ouroboros` (`upstream/ouroboros`, не `main`);
   **не поднимать версию**. `VERSION`, версия в `pyproject.toml`, editable root в
   `uv.lock`, `web/package.json`, `GATEWAY_CONTRACT_VERSION`, бейджи/ссылки в README,
   заголовок версии в ARCHITECTURE и release-теги оставлять без изменений
   (их назначают сопровождающие на финальном дереве).
4. Закоммитить изменение, затем требовать пустой `git status --short`. Не коммитить
   секреты, локальные настройки, runtime-состояние, логи, кэши, прогоны бенчмарков,
   сгенерированные ревью-пакеты, build-артефакты.
5. Верифицировать (`make test` и пр.), фиксировать точные команды, результаты и
   коды выхода. Что не удалось запустить — `NOT_RUN` + причина, а не «прошло».
6. **Рецензия в отдельном контексте агента**: финальный diff заморозить и отдать
   отдельному агенту/сессии (в контексте автора ревью не засчитывается). Основной
   путь — agentic checklist review по `docs/CHECKLISTS.md`: JSON-массив по всем восьми
   пунктам (`intent_alignment`, `forgotten_touchpoints`, `cross_surface_consistency`,
   `regression_surface`, `prompt_doc_sync`, `architecture_fit`, `cross_module_bugs`,
   `implicit_contracts`); PASS-строки обязательны и обоснованы конкретным артефактом;
   критический FAIL называет точный файл/символ. Валидировать receipt локально:
   `python scripts/validate_scope_receipt.py path/to/receipt.json` (валидирует SHAPE,
   а не истинность — это не вердикт).
   Если отдельного контекста нет — `NOT_RUN` с объяснением, не подменять
   самоконтекстным ревью.
7. Открыть PR по шаблону `.github/PULL_REQUEST_TEMPLATE.md`; вложить свидетельства
   верификации и ревью, JSON чек-листа, базовый/целевой SHA. Рецензия — публичные
   свидетельства; проверить вложения на секреты/приватные пути.

Maintainer-инструмент рецензии (крупные окна) — `scripts/run_external_review.py
--contributor`; по умолчанию это не путь вклада (см. CONTRIBUTING.md).

## Примечания

- `BIBLE.md` — «конституция» Ouroboros: определяет, кто он, а не как работает.
  Меняется только через явный рецензируемый релиз и не должен противоречить
  существующим положениям. `identity.md` обязан оставаться присутствующим файлом
  как канал непрерывности.
- Храните записи этого файла на русском языке; технические артефакты (код, пути,
  команды) не переводятся.
